# 청소모아 (CheongsoMoa)

청소 **도급 중개 플랫폼**. 고객이 요청서를 한 장 쓰면 검증된 청소 업체들이 견적을 보내고,
고객이 비교해 고른 뒤 **선결제(에스크로)** 하면 플랫폼이 금액을 보관했다가
작업 확인 후 **중개 수수료를 제한 금액을 업체에 정산**합니다.

```
고객 요청서 → 업체 견적 N개 → 고객 선택 → 안전결제(예치) → 작업 → 고객 확인 → 업체 정산(수수료 차감)
```

---

## 빠르게 실행하기

PostgreSQL 이 필요합니다. 접속 정보를 `.env.local` 에 넣으세요.

```bash
cp .env.example .env.local     # DATABASE_URL 을 본인 환경에 맞게 수정
npm install
psql "$DATABASE_URL" -f supabase/migrations/0001_init.sql   # 스키마 생성
npm run seed                   # 데모 데이터 적재 (기존 데이터는 지워집니다)
npm run dev
# http://localhost:3000
```

테스트:

```bash
npm run typecheck
npx playwright test            # 실행 전에 DB를 시드 상태로 되돌립니다
```

### 데모 계정 (비밀번호 공통: `cheongso1234`)

| 역할 | 이메일 | 들어가는 곳 |
| --- | --- | --- |
| 고객 | `customer@demo.kr` | `/my` — 견적 비교·결제·작업 확인·후기 |
| 업체 | `partner@demo.kr` | `/partner` — 요청 확인·견적 제출·작업 보고·정산 |
| 운영자 | `admin@demo.kr` | `/admin` — 업체 심사·거래 현황·수수료 정책 |

데모 고객 계정에는 **네 가지 상태의 건**이 미리 들어 있습니다.
견적 4개가 도착한 열린 요청 / 작업 중인 건 / 고객 확인을 기다리는 건 / 정산까지 끝난 건.

## 왜 이렇게 만들었나

### 고객이 느끼는 문제
- 업체마다 전화해서 견적을 물어봐야 하고, 부르는 값이 다른 이유를 알 수 없다.
- 처음 보는 업체에 선결제하기가 불안하다.
- 청소가 엉망이어도 이미 돈을 준 뒤라 말하기 어렵다.

**대응**
- `카테고리별 평당 기준 단가 공개` + `30초 예상 견적 위젯` — 요청 전에 대략의 금액을 먼저 안다.
- `안전결제(에스크로)` — 결제금은 작업 확인 전까지 플랫폼이 보관. 업체가 안 오면 100% 환불.
- `견적 카드 비교` — 금액만이 아니라 평점·완료 건수·무상 A/S 기간·업체 메시지를 한 화면에서 비교.
- `상세 주소·연락처 비공개` — 결제가 끝난 업체에게만 열린다. 요청만 하고 전화 폭탄을 맞지 않는다.

### 업체가 느끼는 문제
- 광고비·입점비를 먼저 내는데 일감은 보장되지 않는다.
- 견적 내러 갔다가 헛걸음하고, 작업 후 대금을 못 받기도 한다.
- 오래 잘해도 수수료가 그대로다.

**대응**
- `입점비·월 이용료·견적 제출 비용 0원` — 성사된 건에만 수수료.
- `결제된 건만 배정` — 고객이 선결제한 뒤에야 주소가 열리므로 노쇼·미수금이 구조적으로 없다.
- `등급제 수수료 15% → 12% → 10%` — 완료 건수와 평점이 쌓일수록 내려간다.
- `견적 작성 화면에 실 정산액 실시간 표시` — 수수료를 떼고 얼마가 남는지 보면서 금액을 정한다.
- `경쟁 현황 공개` — 제출된 견적 수·최저가·평균가를 보고 값을 조정한다.

### 플랫폼 수익
결제 금액 × 등급별 수수료율(10~15%). PG 결제 수수료와 정산 이체 수수료는 플랫폼이 부담하므로
실질 마진은 표시 요율보다 2~3%p 낮습니다. 고객에게는 수수료를 청구하지 않습니다.

## 상태 흐름

**요청(CleaningRequest)**
`open` → `selected` → `paid` → `in_progress` → `completed` → `settled` (또는 `canceled`)

**주문(Order)**
`pending_payment` → `escrow` → `in_progress` → `completed` → `settled`

| 전이 | 누가 | 무슨 일이 일어나나 |
| --- | --- | --- |
| 견적 선택 | 고객 | 주문 생성. 선택 시점의 등급 요율로 수수료·정산액 확정. 나머지 견적은 자동 미선정 |
| 결제 | 고객 | 금액이 에스크로로 예치되고 업체에 주소·연락처 공개 |
| 작업 시작 / 완료 보고 | 업체 | 상태 기록. 고객 화면 타임라인에 반영 |
| 작업 확인 | 고객 | 수수료 차감 후 정산. 업체 완료 건수 증가 → 등급 재계산 |
| 강제 정산 | 운영자 | 고객이 자동 확정 기간(기본 7일)까지 확인하지 않은 건 처리 |

수수료는 **견적 선택 시점**에 주문에 박제됩니다. 운영자가 나중에 요율을 바꿔도 이미 체결된 건은 변하지 않습니다.

## 코드 구조

```
src/
├── app/                      # App Router 페이지 (서버 컴포넌트 기준)
│   ├── my/ partner/ admin/   # 역할별 대시보드 (각 layout에서 접근 제어)
│   └── ...                   # 공개 페이지
├── actions/                  # 서버 액션 (auth / request / order / partner / admin)
├── components/               # UI 프리미티브 + 폼 클라이언트 컴포넌트
└── lib/
    ├── types.ts              # 도메인 모델
    ├── catalog.ts            # 서비스 8종, 옵션, 지역, 단가표
    ├── estimate.ts           # 평당 단가 × 건물 계수 × 옵션 → 예상 견적 범위
    ├── fees.ts               # 등급별 수수료율, 정산액 계산, 등급 재평가
    ├── service.ts            # 요청·견적·주문·리뷰 도메인 로직
    ├── auth.ts               # scrypt 비밀번호, 쿠키 세션
    └── db.ts                 # Postgres 어댑터 (커넥션, 트랜잭션, 행 매퍼)
```

- **상태 변경은 전부 서버 액션**을 거칩니다. 클라이언트에서 직접 저장소를 만지는 경로가 없습니다.
- **여러 행을 바꾸는 작업은 트랜잭션**입니다. 견적 선택은 주문 생성·낙찰 처리·나머지 견적 미선정·요청 상태 변경을 한 번에 커밋합니다.
- 앱이 의존하던 불변식을 **DB 제약으로도 막습니다**: 요청·업체당 열린 견적 1개, 요청당 결제 대기 주문 1개 (부분 유니크 인덱스).
- **권한 검사는 도메인 로직 안**(`service.ts`)에도 있습니다. 액션이 뚫려도 남의 주문을 결제할 수 없습니다.
- `estimate.ts` / `fees.ts` 는 순수 함수라 서버·클라이언트 양쪽에서 같은 계산을 씁니다.
  (견적 폼에서 실시간으로 보이는 금액과 서버가 저장하는 금액이 어긋나지 않습니다.)

## 운영 전환 시 바꿔야 할 것

이 저장소는 **동작하는 제품 프로토타입**입니다. 실서비스로 올리려면:

| 지금 | 운영 |
| --- | --- |
| 모의 결제 (`payOrder`) | 토스페이먼츠·PortOne 등 PG 연동 + 웹훅으로 결제 확정. 에스크로 정산은 지급대행 계약 필요 |
| 없음 | 알림톡/SMS (견적 도착, 작업 D-1, 확인 요청), 이메일 |
| 수동 심사 | 국세청 사업자 진위확인 API, 보험 증권 파일 업로드·검수 |
| 자동 확정 미실행 | 크론/큐로 `autoConfirmDays` 경과 건 자동 정산 |
| 주소 문자열 입력 | 카카오/도로명주소 API |
| 사진 필드만 존재 | S3 등 오브젝트 스토리지 업로드 (요청 사진, 작업 전후 리포트) |

법적으로는 통신판매중개업 신고, 결제대금예치(에스크로) 관련 요건, 개인정보 처리방침 검토가 필요합니다.
`/terms`, `/privacy` 문안은 예시이며 법률 검토 전 그대로 쓰면 안 됩니다.
